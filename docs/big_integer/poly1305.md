# Poly1305 Message Authentication Code

## 1. Overview

**Poly1305** is a cryptographic message authentication code (MAC) designed by **Daniel J. Bernstein**. It provides fast, secure message authentication using polynomial evaluation in a prime field. Poly1305 is widely deployed in modern cryptographic protocols, including TLS 1.3, SSH, and IPsec, often paired with the ChaCha20 stream cipher (ChaCha20-Poly1305).

A MAC is a short piece of information used to authenticate a message and confirm its integrity. Poly1305 takes a secret key and a message of arbitrary length, producing a 16-byte authentication tag. Any modification to the message or use of an incorrect key will result in a different tag, allowing detection of tampering or forgery attempts.

**Historical Context**: Poly1305 was introduced by Bernstein in 2005 as part of a suite of fast, secure cryptographic primitives. It was designed to be:
- **Extremely fast**: Optimized for modern processors
- **Provably secure**: Security reduces to polynomial evaluation in a finite field
- **Simple**: Minimal code complexity for easier verification

Poly1305 has been standardized in RFC 8439 (ChaCha20-Poly1305 for IETF Protocols) and RFC 7539, and is one of the few MACs approved for use in TLS 1.3.

**Security Note**: This implementation uses the `num-bigint` library, which **does not guarantee constant-time operations**. For production cryptographic applications, a constant-time implementation is essential to prevent timing side-channel attacks.

## 2. Mathematical Foundation

### 2.1 Problem Definition

**Message Authentication Code (MAC)**:
- **Input**: 
  - Key $k$ (256 bits / 32 bytes)
  - Message $m$ (arbitrary length)
- **Output**: 
  - Tag $t$ (128 bits / 16 bytes)
- **Security Property**: 
  - Without knowing $k$, an attacker cannot forge a valid tag for any message with probability better than $2^{-128}$

### 2.2 Mathematical Model

Poly1305 is based on **polynomial evaluation in a prime field** $\mathbb{Z}_p$ where:

$$p = 2^{130} - 5$$

This prime was chosen for efficient modular arithmetic on 64-bit architectures.

#### 2.2.1 Key Structure

The 256-bit key is split into two parts:
- **$r$** (first 128 bits): Used as the evaluation point for the polynomial
- **$s$** (last 128 bits): Added to the result for final tag

The value $r$ is **clamped** by clearing specific bits to ensure it falls in a secure range:

$$r' = r \land \texttt{0x0ffffffc0ffffffc0ffffffc0fffffff}$$

This clamping:
- Clears the top 4 bits of each 32-bit limb
- Clears the bottom 2 bits of every 32-bit limb except the last
- Ensures $r < 2^{124}$ and certain algebraic properties

#### 2.2.2 Polynomial Construction

The message $m$ is divided into 16-byte blocks $m_1, m_2, \ldots, m_n$:

1. Each block is interpreted as a little-endian 128-bit integer
2. A single bit (the 129th bit) is appended to each block
3. The last block (if incomplete) is padded with zeros, then the bit is appended

This constructs coefficients $c_1, c_2, \ldots, c_n$ where:

$$c_i = m_i + 2^{8 \cdot |m_i|}$$

(The $2^{8 \cdot |m_i|}$ term is the appended bit, where $|m_i|$ is the byte length of block $i$.)

#### 2.2.3 Polynomial Evaluation

The authentication tag is computed as:

$$\text{tag} = \left( \sum_{i=1}^{n} c_i \cdot r^{n-i+1} \bmod p \right) + s \bmod 2^{128}$$

This is equivalent to evaluating the polynomial:

$$P(x) = c_1 x^n + c_2 x^{n-1} + \cdots + c_n x$$

at $x = r$ in the field $\mathbb{Z}_p$, then adding $s$ and reducing modulo $2^{128}$.

**Horner's Method** is used for efficient evaluation:

$$\text{acc} = 0$$
$$\text{for } i = 1 \text{ to } n:$$
$$\quad \text{acc} = ((\text{acc} + c_i) \cdot r) \bmod p$$
$$\text{tag} = (\text{acc} + s) \bmod 2^{128}$$

### 2.3 Security Properties

**Theorem (Information-Theoretic Security)**: If $r$ is chosen uniformly at random from the clamped space, then for any message $m$ and any tag $t$, the probability that a different message $m'$ produces the same tag is at most:

$$\Pr[\text{Poly1305}_r(m') = t] \leq \frac{\lceil |m'| / 16 \rceil}{2^{106}}$$

**Proof Sketch**: 
- Each message defines a polynomial of degree $n = \lceil |m| / 16 \rceil$
- Two different messages define different polynomials
- A polynomial of degree $n$ has at most $n$ roots in any field
- The clamped $r$ space has approximately $2^{106}$ values
- Thus, collision probability is bounded by $n / 2^{106}$

**Key Properties**:
1. **One-time key**: Each $(r, s)$ pair should be used for only one message
2. **Deterministic**: Same key and message always produce the same tag
3. **Fast**: Approximately 3-4 CPU cycles per byte on modern hardware
4. **Parallelizable**: Can be vectorized using SIMD instructions

**Comparison with HMAC-SHA256**:
- Poly1305: ~3-4 cycles/byte, information-theoretic security
- HMAC-SHA256: ~10-15 cycles/byte, security based on collision resistance
- Poly1305 is 3-5× faster with comparable security for one-time use

## 3. Algorithm Description

### 3.1 Intuition

Think of Poly1305 as computing a **polynomial hash**:

1. **Break message into chunks**: Split the message into 16-byte blocks
2. **Create coefficients**: Each block becomes a coefficient with an extra bit
3. **Evaluate polynomial**: Compute the polynomial at a secret point $r$
4. **Add secret offset**: Add $s$ to make the result unpredictable without the full key
5. **Truncate**: Take only the lower 128 bits as the final tag

The security comes from the fact that:
- Finding $r$ from tags requires solving discrete logarithm-like problems
- Forging a tag without $r$ requires guessing one of few roots of a polynomial
- The extra bit ensures block boundaries are authenticated (padding oracle resistance)

### 3.2 Pseudocode

```
struct Poly1305:
    p = 2^130 - 5                    // Prime modulus
    r: BigUint                        // Evaluation point (clamped)
    s: BigUint                        // Secret offset
    acc: BigUint = 0                  // Accumulator

function set_key(key: [u8; 32]):
    r = little_endian_to_int(key[0..16])
    s = little_endian_to_int(key[16..32])
    clamp_r()

function clamp_r():
    // Clear specific bits for security
    r &= 0x0ffffffc0ffffffc0ffffffc0fffffff

function add_msg(msg_block: [u8; 16], block_len: u64):
    // Convert block to number (little-endian)
    n = little_endian_to_int(msg_block)
    
    // Set bit at position (block_len * 8)
    n |= (1 << (block_len * 8))
    
    // Horner's method step
    acc = acc + n
    acc = acc * r
    acc = acc mod p

function get_tag() -> [u8; 16]:
    result = (acc + s) mod 2^128
    return int_to_little_endian_bytes(result, 16)

// Complete MAC computation
function poly1305_mac(key: [u8; 32], message: [u8]) -> [u8; 16]:
    mac = Poly1305()
    mac.set_key(key)
    
    // Process full 16-byte blocks
    for i = 0 to (len(message) / 16) - 1:
        block = message[i*16 .. (i+1)*16]
        mac.add_msg(block, 16)
    
    // Process final partial block (if any)
    remaining = len(message) mod 16
    if remaining > 0:
        final_block = [0; 16]
        final_block[0..remaining] = message[len(message)-remaining..]
        mac.add_msg(final_block, remaining)
    
    return mac.get_tag()
```

### 3.3 Step-by-Step Example

**Example**: Authenticate message `"Cryptographic Fo"` (16 bytes)

**Step 1: Key Setup**
```
key = [0x85, 0xd6, 0xbe, 0x78, ..., 0x1b]  // 32 bytes
r_raw = 0x337f6d555778bed6 || 0xa80642fe52447f  // First 16 bytes as 128-bit LE
s = 0x1bf549af41f6bffd || 0x8a800301a8064d42   // Last 16 bytes as 128-bit LE
```

**Step 2: Clamp r**
```
r = r_raw & 0x0ffffffc0ffffffc0ffffffc0fffffff
r = 0x337f6d555778bed4 || 0x280642fe52447f    // After clamping
```

**Step 3: Process Block**
```
msg = "Cryptographic Fo" = [0x43, 0x72, 0x79, 0x70, 0x74, ..., 0x46, 0x6f]
n = little_endian_to_int([0x43, 0x72, 0x79, 0x70, 0x74, ..., 0x46, 0x6f])
n = 0x6f46206369687061726720746f697270794372

// Set bit at position 16 * 8 = 128
n |= (1 << 128)
n = 0x16f46206369687061726720746f697270794372  // Note the extra '1' prefix
```

**Step 4: Horner's Method**
```
acc = 0
acc = (acc + n) mod p
acc = 0x16f46206369687061726720746f697270794372 mod (2^130 - 5)
acc = 0x16f46206369687061726720746f697270794372  // (smaller than p, no reduction)

acc = (acc * r) mod p
acc = ... (large multiplication and modular reduction)
```

**Step 5: Final Tag**
```
result = (acc + s) mod 2^128
tag = int_to_bytes_le(result, 16)
tag = [0xa8, 0x06, 0x1d, 0xc1, 0x30, 0x51, 0x36, 0xc6, 
       0xc2, 0x2b, 0x8b, 0xaf, 0x0c, 0x01, 0x27, 0xa9]
```

**Expected Output**: `a8061dc1305136c6c22b8baf0c0127a9` (as hex)

## 4. Complexity Analysis

### 4.1 Time Complexity

**Per-Block Processing**: $O(1)$ (amortized)
- One addition: $O(1)$ in hardware, $O(\log p)$ for big integers
- One multiplication: $O(1)$ in hardware, $O((\log p)^2)$ for naive big int
- One modular reduction: $O(1)$ in hardware, $O(\log p)$ for big integers

**Complete Message**: $O(n)$ where $n$ is message length in blocks

**Practical Performance**:
- **Hardware implementation**: ~3-4 CPU cycles per byte
- **Optimized software**: ~5-10 cycles per byte
- **This implementation (big integers)**: ~1000-10000 cycles per byte (much slower)

**Comparison**:
| Algorithm | Cycles/Byte | Notes |
|-----------|-------------|-------|
| Poly1305 (optimized) | 3-4 | Vectorized, constant-time |
| HMAC-SHA256 | 10-15 | Cryptographic hash based |
| AES-GCM | 2-3 | Hardware acceleration |
| This implementation | ~1000+ | Big integer library, non-constant-time |

### 4.2 Space Complexity

**Key Storage**: $O(1)$
- Fixed 256-bit key: $r$ (128 bits) + $s$ (128 bits)

**Accumulator**: $O(1)$
- Single 130-bit value (fits in two 64-bit words in optimized implementations)

**Message Processing**: $O(1)$
- Streaming algorithm: processes one block at a time
- No need to store entire message

**Total Space**: $O(1)$ auxiliary space (not counting input/output)

- Creates large constants cleanly


- Bitwise AND for clamping operation
- Works on arbitrary-precision integers

**Little-Endian Byte Order**:
- Crypto standards typically use little-endian
- `from_bytes_le()` and `to_bytes_le()` handle conversion
- Critical for interoperability with other implementations

**Security Warning**:
```rust
// Note that the Big Integer library we are using may not be suitable for

```
- Big integer operations may leak timing information
- Production code should use constant-time arithmetic
- Consider `subtle` crate for constant-time operations

### 5.2 Edge Cases

| Edge Case | Handling | Notes |
|-----------|----------|-------|
| **Empty message** | Process zero blocks | Tag = $(s) \bmod 2^{128}$ |
| **Single block (16 bytes)** | Normal processing | Most common case |
| **Partial block (< 16 bytes)** | Zero-pad, set bit at correct position | Crucial for security |
| **Very long message** | Stream processing | No memory limit |
| **All-zero key** | Works but insecure | Should validate key entropy |
| **Reused key** | Insecure! | Each key should authenticate only one message |
| **Non-16-byte tag** | Truncate to 16 bytes | Implementation pads if needed |

**Critical Security Considerations**:

1. **One-time keys**: Never reuse $(r, s)$ for different messages
   - Use a key derivation function (KDF) to generate unique keys
   - Common pattern: Nonce + master key → unique Poly1305 key

2. **Padding validation**: The appended '1' bit prevents length-extension attacks
   ```rust
   n.set_bit(msg_bytes * 8, true);  // Must be at exact message length
   ```

3. **Tag truncation**: Always use full 16-byte tag
   - Truncating reduces security proportionally
   - 8-byte tag → only 64-bit security

4. **Constant-time comparison**: When verifying tags, use constant-time equality
   ```rust
   // DON'T: if computed_tag == received_tag
   // DO: use subtle::ConstantTimeEq
   ```

## 6. Real-World Applications

### 6.1 Software Engineering Use Cases

**1. ChaCha20-Poly1305 AEAD (Authenticated Encryption)**
- **TLS 1.3**: Mandatory cipher suite `TLS_CHACHA20_POLY1305_SHA256`
- **OpenSSH**: Default encryption since version 6.5
- **WireGuard VPN**: Core cryptographic primitive
- **Signal Protocol**: End-to-end encrypted messaging
- **QUIC Protocol**: Google's transport protocol (now HTTP/3)

**Integration Example**:
```rust
// Typical AEAD usage
fn encrypt_and_authenticate(key: &[u8; 32], nonce: &[u8; 12], 
                            plaintext: &[u8], aad: &[u8]) -> (Vec<u8>, [u8; 16]) {
    let cipher_key = &key[..32];
    let poly_key = generate_poly1305_key(cipher_key, nonce);
    
    let ciphertext = chacha20_encrypt(cipher_key, nonce, plaintext);
    let tag = poly1305_mac(&poly_key, &[aad, &ciphertext].concat());
    
    (ciphertext, tag)
}
```

**2. Disk Encryption**
- **dm-crypt**: Linux disk encryption with ChaCha20-Poly1305
- **VeraCrypt**: Optional cipher for volume encryption
- Faster than AES-GCM on CPUs without AES-NI

**3. Network Protocols**
- **IPsec**: ESP with ChaCha20-Poly1305 (RFC 7634)
- **RTP**: Real-time transport protocol (RFC 7714)
- **DTLS**: Datagram TLS with ChaCha20-Poly1305

**4. File Integrity**
- **Age encryption tool**: Modern file encryption format
- **Minisign**: Digital signature tool (uses Poly1305 for verification)
- **Tarsnap**: Online backup with Poly1305 authentication

**5. Embedded Systems**
- **IoT Devices**: Low-power cryptography (no AES hardware)
- **Microcontrollers**: Efficient on ARM Cortex-M processors
- **Automotive**: CAN bus message authentication

### 6.2 Related Algorithms

**Other Message Authentication Codes**:

1. **HMAC-SHA256** - Hash-based MAC
   - Security: Based on collision resistance of SHA-256
   - Speed: ~10-15 cycles/byte
   - When to use: When SHA-256 is already available, multi-use keys

2. **AES-GCM** - Galois/Counter Mode
   - Security: Based on AES block cipher
   - Speed: ~2-3 cycles/byte (with AES-NI)
   - When to use: Hardware acceleration available, need AEAD

3. **BLAKE3** - Modern hash function with keyed mode
   - Security: Based on BLAKE3 hash function
   - Speed: ~3-4 cycles/byte
   - When to use: Need hash + MAC in one primitive

4. **GHASH** - Galois field hash (used in GCM)
   - Security: Similar to Poly1305
   - Speed: ~2-3 cycles/byte (with PCLMULQDQ)
   - When to use: Part of AES-GCM

**Comparison Table**:

| MAC | Key Use | Speed (cycles/byte) | Security Basis | AEAD Cipher |
|-----|---------|---------------------|----------------|-------------|
| Poly1305 | One-time | 3-4 | Polynomial evaluation | ChaCha20-Poly1305 |
| HMAC-SHA256 | Multi-use | 10-15 | Hash collision resistance | - |
| GCM-GHASH | One-time | 2-3 | Polynomial evaluation | AES-GCM |
| BLAKE3-keyed | Multi-use | 3-4 | Hash security | - |

**Authenticated Encryption (AEAD) Schemes**:
- **ChaCha20-Poly1305**: Software-friendly, constant-time
- **AES-GCM**: Hardware-accelerated on modern CPUs
- **AES-CCM**: Simpler than GCM, but slower
- **Ascon**: Winner of NIST lightweight crypto competition

**When to Use Poly1305**:
- ✅ Need high-speed MAC without hardware acceleration
- ✅ Implementing ChaCha20-Poly1305 AEAD
- ✅ Embedded systems without AES instructions
- ✅ Side-channel resistance important (easier to implement constant-time)
- ❌ Need multi-use keys (use HMAC instead)
- ❌ AES-NI available (AES-GCM may be faster)
